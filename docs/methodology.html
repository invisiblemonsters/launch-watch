Methodology

Each launch gets a deterministic 0-100 score. Higher means more risk signals. A risk signal is a measurable property that has been common in failed or abusive launches (for example, one wallet controlling owner functions). It is not a finding about any team's intent, and many legitimate projects carry several.

How the score is built

  • Every check returns risk signal (adds its fixed weight), pass or info (adds 0), or unknown (adds 3).
  • Unknown is honest: when a check cannot run with free public data (for example there is no free sell simulator for Robinhood Chain), it is shown as unknown and adds a small, fixed uncertainty weight so missing data never looks safe. It is never guessed.
  • Privileged-function points are multiplied by 0.5 when owner() is provably 0x0 or dead (renounced), because other roles may still call them. When there is no owner (or it is renounced), the contract uses OpenZeppelin AccessControl, no account holds a role (RoleGranted/RoleRevoked logs since deployment, hasRole on the deployer) and no initializer is still open, the functions are shown as informational with 0 points.
  • The total is capped at 100. Bands: 0-24 LOW, 25-49 MODERATE, 50-74 ELEVATED, 75-100 HIGH.
  • On-chain reads are pinned to one block per scan. DexScreener, GeckoTerminal and GoPlus are live APIs; their responses are saved in each launch's raw JSON so any score can be re-derived.

Data sources

Public, keyless sources only: chain RPC (Robinhood Chain 4663, Base 8453), Sourcify, Blockscout, GoPlus, honeypot.is (Base), DexScreener, GeckoTerminal, Google DNS-over-HTTPS and RDAP. Launch posts come from public X search. The GoPlus and honeypot.is query pattern is reused from the open-source token-launch-scan.

Known limits

  • No free sell simulation exists for Robinhood Chain, so that check is always unknown there.
  • LP lock status cannot be read for bonding-curve (Pons) pools or Uniswap v3/v4 positions; it is computed for V2 pairs and taken from GoPlus where available.
  • The bytecode-only function scan matches 64 exact common signatures; renamed functions can be missed. Beyond the role-holder check above, access control on those functions is not analysed.
  • Deployer contract counts include direct deployments only, not factory launches (Pons, Clanker, ape.store).
  • Hosting overlap is only as good as the watchlist. Shared CDN and PaaS ranges are excluded on purpose.
  • Scores are a snapshot. Owners can change settings, add or remove liquidity at any time after a scan.

What is not listed

A scored launch is left off this site when its evidence is incomplete or broken: a flagged check without a verifiable link, a scan that aborted, a malformed record, or a launch post that turned out to belong to a third party or to point at a different contract. These are not judgments about the projects. Excluded so far: 3.

  • Launch post belongs to a third party or names a different contract: 3

Known-dead evidence links are repaired before publishing (for example, a Sourcify link for a contract that is only verified on Blockscout is replaced by the Blockscout source link). Hosting facts are stated as infrastructure overlap only.

Corrections

If a team shows that a signal is wrong (for example a multisig owner misclassified), it is corrected publicly. Email metatron@mail.grokbot.com with the chain, address and the evidence.
